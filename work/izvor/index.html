What it is

I wrote izvor as a typed language with an interpreter and a compiler. A source file can run directly, or the compiler can emit C and pass it to a native compiler. The command line exposes those choices as run, emit and build. The emitted C is available to read before building a binary.

The language has integer and boolean expressions. Functions can call other functions, including themselves. Declarations distinguish mutable variables from values that cannot be reassigned. The syntax tree also represents conditional branches and loops.

How it works

The front end in src/main.c reads the source, asks the parser for a Program, and checks it before execution. src/ast.h defines tagged unions for expressions and statements. Each expression carries a source offset and a type. A binary expression holds its operator and pointers to its operands, so the later stages never look at source text again.

The interpreter walks the checked tree. The code generator uses that same tree to emit C. For a native build, build_binary opens a pipe and starts the C compiler in a child process. The parent writes generated source into the pipe and waits for the compiler’s exit status. A failed build becomes an error returned to the caller.

The hard part

I had to preserve evaluation order when translating expressions. C does not guarantee the order in which function arguments are evaluated. If an izvor expression calls functions that print, copying the expression straight into C can change what gets printed. Arithmetic failures also make the order observable.

This is the start of tests/golden/evaluation-order.iz. say prints its argument and returns it, so the order things were evaluated in shows up in the output. For the first print, both paths have to print 1, 2, 3 and then 7.

fn say(n: Int) -> Int {
    print(n);
    return n;
}

print(say(1) + say(2) * say(3));
print(say(4) - say(5));
let x = say(6) < say(7) && say(8) == 8;
print(x);

In src/codegen.c, has_effects identifies expressions whose evaluation matters. The generator can store intermediate results in temporary variables before using them. It handles short circuit boolean expressions separately so an operand that should be skipped stays skipped. tests/golden/evaluation-order.iz exercises printed function calls inside arithmetic and conditions. The golden target in Makefile compares both execution paths against the same expected output, including diagnostics.

Where it stands

There are 41 golden programs, and each one has to print the same bytes from the interpreter and from the compiled binary. CI also fuzzes the front end with 20,000 inputs from a fixed seed on Linux and macOS. The native build needs a C compiler on the machine. The types are Int and Bool, plus void for functions that return nothing. There are no strings or collections yet. The source is public, and I wrote the build up as a line by line course. Both are linked above.
