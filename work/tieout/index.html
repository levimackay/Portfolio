01

What it is

I wrote tieout for the step where a tax preparer compares a client’s books with the previous filed return.

  • It reads exported files and explains differences that it can trace to evidence.
  • It drafts correcting entries for the preparer to review.
  • An unexplained difference remains an item for a person to investigate, with no proposed entry attached.
Read the rest

The application runs on the preparer’s computer. Its workflow starts with exported balances and the filed return, then asks the preparer to confirm the extracted return figures. Approval is a separate step from calculation. Only approved entries belong in the journal entry import file, so finding a possible correction does not itself authorize posting it.

02

How it works

tieout/return_pdf.py invokes pdftotext with layout preservation and looks for Schedule L in the extracted text.

  • Its Reading structure holds values alongside uncertain lines and a balance check.
  • If the external reader is unavailable, the application allows manual entry.
  • A PDF with no text layer gets an error, never guessed balances.
Read the rest

The engine maps account amounts to return lines. LineResult stores the books amount and filed amount, along with evidence explaining the difference. Its remainder calculation subtracts the explained pieces. JournalLine holds debit and credit values as Decimal, and ProposedEntry computes whether those sides balance. The result separates proposed entries from checks and items that need a preparer’s decision.

03

The hard part

I had to distinguish an adjustment that belongs in the books from one already posted there.

  • Repeating a preparer’s adjustment would create another error.
  • The engine searches journal rows for matching accounts and debit and credit amounts.
  • A matched row is removed from the candidate pool, so the same ledger row cannot satisfy repeated adjustment lines.
Read the rest

The posting date also changes how a correction should be represented. When the previous year is closed, the application drafts an opening entry and moves income and expense effects into the relevant equity account. When it is open, the adjustment stays at the previous year end. tests/test_tieout.py checks the opening entry transformation and that proposed entries balance. The engine separately checks for an opening entry already present in the ledger.

04

Where it stands

I have only run tieout on sample files.

  • The QuickBooks readers have not been checked against a client’s file, and the Desktop layout comes from documentation.
  • The return reader has not been checked against returns produced by commercial preparation software.
  • There is no direct QuickBooks connection: files enter by export and entries return by import.
  • There are 116 tests, and all of them run against sample data. That is not the same as a real client’s books, which is the next thing it has to face.
