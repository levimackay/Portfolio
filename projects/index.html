C · Compilers · In progress

izvor

A programming language built from scratch in C: a lexer, a recursive-descent parser, and a tree-walking interpreter, then a bytecode compiler and a stack VM to replace the back half the way real languages do it.

I'm working through it by hand, task by task, and a task is done when its test passes. The window on this panel is a recorded session from the repo as it stands: the lexer dumping tokens, the parser printing the syntax tree, and the evaluator computing the answer, including what a parse error looks like.

Challenge
Understanding a language implementation by building one, not reading about one: source text to tokens, tokens to AST, AST to a value.
Approach
An 8-phase roadmap from C fundamentals through a stack-based VM, roughly 70–90 hours of work, each task shipped with an assert-based test. Compiled with -Wall -Wextra -fsanitize=undefined from the first file.
Current state
Phase 2 in progress. The lexer is done and the recursive-descent expression parser and evaluator shown in the recording are the newest tasks to go green. The session is genuine, unedited output.

C · Systems · Planned build

minidb

A single-file database engine built by hand in C: binary file formats, a pager with fixed-size pages, B-trees, cursors, and a small SQL parser over the top.

The full roadmap and Phase 0 scaffolding are written and committed; my own implementation hasn't started yet. The panel shows the actual roadmap, because that's what exists: there is no REPL to screenshot, so I'm not showing one.

Challenge
Knowing what a database actually does under the query layer: how rows become bytes, how bytes become pages, how a B-tree makes lookup logarithmic.
Approach
Eight phases from binary file I/O to a write-ahead log, ~43–65 hours, phases 0–1 fully scaffolded with stubs, tests, and a reference. Sequenced after izvor, which covers the C this project assumes.
Current state
Roadmap and scaffolding committed; implementation not started. That is what "planned build" means here.

Swift 6 · iOS 26 · Phase 0

FORGE

A native iOS personal development system that turns long-term goals into adaptive daily missions: you complete a mission, your skill progress updates, and the next recommendation gets better.

Phase 0 is complete: product definition, architecture, decision records, design language, and roadmap, written so a stranger could explain what version 1 will and won't contain. There is no app UI yet, and this panel doesn't pretend otherwise: what you're looking at is the actual roadmap, phase by phase, with the one in-progress phase marked.

Challenge
Long-term goals fail at the daily level: nothing translates "where I want to be in two years" into "what I should do today."
Approach
A closed loop (goal, skills, progress, recommended mission, completion, updated progress, better recommendations) with a deterministic scoring function that can justify each recommendation in a sentence. Swift 6, strict concurrency from the first commit.
Current state
Phase 1 (core loop) in progress: the Xcode project and the ForgeKit / ForgeData package split are in place with strict concurrency on from the first commit. The domain model, persistence, and the scoring function come next. Speed is explicitly not a goal.

Python · Ollama · Shipped

Lydia

A coding agent that runs entirely on your own machine. It reads your code, edits files, runs commands, drives git, and checks its own work by running your tests, all through a local Ollama model. No API key, no account, and nothing leaves the machine.

Its implementation was written with heavy AI assistance and the README says so plainly. What is mine is the architecture, the tool surface and its safety model, the decision to stay local only, and the review of everything that lands. Two of the merged pull requests came from people I have never met, and every change has to pass the suites on Python 3.11 through 3.13 before it goes in.

Challenge
The useful coding agents are metered, need an account, and send your code to somebody else's server. The tradeoff is real: a local model is smaller and slower, so the design has to earn its keep on the routine work.
Approach
An agent loop over a small tool surface, one diff per approval rather than whole-file rewrites, and the model checks itself by running the project's own tests and reading the failure.
Current state
On PyPI, 36 stars and 8 forks, 475 tests across 56 files running green in CI, and two merged pull requests from outside contributors.
